# 测试库探查：产业链岗位、典型任务与 JD 聚类

2026-11-23 从测试环境的 `ai_crowd_souring_extend`（MySQL 5.7.43-log）执行只读探查。测试库已按学校类型组织岗位目录，并在具体岗位下面增加细分岗位。典型任务表的 74,654 条未删除记录覆盖这两类节点。库里还有独立的 JD 岗位聚类及画像报告，可通过聚类 ID 查询。各查询独立执行。 [表清单](./表清单.csv) · [查询语句与结果](./discovery.json)

## 库的规模

当前账号可见 22 个数据库。本次检查默认业务库，包含 **657 张 InnoDB 表、1 个视图、6,006 个字段、815 个索引及 134 项声明外键**。表清单的行数来自 `information_schema.TABLES.TABLE_ROWS`，是 InnoDB 估计；下文的业务数目来自 `SELECT COUNT`。企业招聘主表 `c_company_position` 实测 2,225,275 条，其中 2,214,298 条未删除、687,092 条同时满足 `publish_state='PUBLISHING'`。

上次库快照有 247 张业务表，具体岗位目录有 3,590 个未删除节点，`school_type` 为空。两次连接的数据源不同，数量差异用于识别环境与口径。 [旧库探查](../2026-11-03/数据库探查.md) · [旧库画像指南](../2026-11-03/岗位画像查询指南.md)

## 产业链岗位目录

`c_industry_chain_position.industry_chain_id → c_industry_chain_info.id`。库内 17,444 个未删除的 `POSITION` 节点关联 98 个产业 ID，全部能连到产业字典，按去空格后的名称去重为 3,904 个名称。

| 目录节点 | 总行数 | 未删除 |
| --- | ---: | ---: |
| 岗位群 `POSITION_GROUP` | 7,698 | 5,665 |
| 具体岗位 `POSITION` | 19,401 | 17,444 |
| 细分岗位 `SUB_POSITION` | 57,433 | 57,210 |

未删除目录节点均有 `school_type`。岗位的学校类型有四种，职业本科代码目前仅出现在专业及专业群。企业招聘学历仍由 `c_company_position.education` 提供。

| 学校类型 | `school_type` | 岗位群 | 具体岗位 | 细分岗位 |

目录表内沿 `子节点.pid → 父节点.id` 查层级。所有具体岗位都连到同产业、同学校类型的未删除岗位群。57,210 个细分岗位中，56,451 个连到同产业、同学校类型的未删除具体岗位，另有 **759 个找不到父节点**，其中 689 个来自普通本科目录。专业用同样的父子字段连到专业群。

画像正文继续存放在 `position_group_portrait`。未删除岗位群中 1,305 个有可解析的 JSON 画像，另有 1 个未删除的高职具体岗位也填了该字段。

## 典型任务和招聘映射

`c_industry_chain_position_typical_task` 共 **81,158 行**，其中未删除 74,654 行，已删除 6,504 行。每条未删除记录的 `industry_chain_position_id` 都不同，恰好连到 17,444 个具体岗位和 57,210 个细分岗位，产业 ID 一致。这是本次数据分布。当前索引仅有 `id` 主键，未对目录节点 ID 声明唯一约束。

`typical_task` 和 `skill_demand` 在所有未删除记录中均为有效 JSON 数组。典型任务为空数组有 378 条，技能为空数组有 680 条，两列均有数组元素的有 73,972 条。未删除记录的创建时间覆盖 2026-11-15 至 2026-11-21，`update_time` 全为空。

查一个节点的典型任务用它在目录表里的 ID。以下 ID 是机器人产业高职目录中的“AGV 实施工程师”。这条细分岗位的上级为“实施工程师”，再上一级是“现场实施与交付岗”。

```sql
SELECT p.position_name, p.school_type, t.typical_task, t.skill_demand
FROM c_industry_chain_position_typical_task t
JOIN c_industry_chain_position p ON p.id = t.industry_chain_position_id
WHERE t.deleted = 0 AND p.deleted = 0
  AND p.id = 4220018025000031274;
```

企业招聘映射沿 `目录节点.id ← c_industry_position_ref.industry_chain_position_id`，再经映射表的 `position_id → c_company_position.id`。实测 878,006 条未删除映射中，**809,466 条（92.2%）指向目录里不存在的节点**。余下的 68,540 条连到 1,039 个具体岗位节点，涉及 45,386 条不同招聘记录，其中 18,841 条在招且未删除。细分岗位本次没有直接连上的招聘映射。需要按细分岗位查招聘时，可沿父链查询上级具体岗位的映射，标明采用了上级范围。查整个产业的招聘需求则走 `c_position_chain`，其粒度不同。

## 聚类后岗位的画像与另外一套标准岗位

| 想查什么 | 表与关联证据 |
| --- | --- |
| 岗位聚类 | `jd_agent_position_cluster`，194 个聚类，属于 13 个岗位分类版本所构成的数据集 |
| 聚类收了哪些 JD | `jd_agent_position_cluster_membership.position_cluster_id → jd_agent_position_cluster.id` 有声明外键。631 条成员记录中的 `jd_id` 均能匹配 `c_company_position.id`，共 320 个不同招聘 ID |
| 聚类后的任务和画像 | `jd_agent_typical_work_task` 1,742 条，`jd_agent_portrait_report` 127 份，均通过外键 `position_cluster_id` 指向岗位聚类。画像覆盖 119 个聚类，正文在 `markdown_content` 和 `json_content`；发布版本表本次为 0 行 |
| 清洗 JD 与标准岗位 | `jd_std_clean_jd.industry_chain_position_id → jd_std_position.id`，`position_id → c_company_position.id`，均有字段注释且 169,715 条清洗 JD 全部匹配两端。标准岗位表有 677 行（634 个岗位、43 个岗位群），均填了 `position_group_portrait` |

这三套对象各有自己的 ID。`jd_std_position` 的 677 个 ID 在产业链目录里均未命中。JD 聚类成员和清洗 JD 可以通过招聘 ID 对照，当前只有 4 条聚类成员记录命中这批清洗 JD。现有字段、外键和数据还不足以把聚类结果或标准岗位直接映射到产业链目录，也无法确认 74,654 条目录任务的生成来源。

查聚类画像时，使用聚类 ID 并保留版本字段：

```sql
SELECT c.id AS cluster_id, c.standard_position_name,
       r.taxonomy_version_id, r.report_version, r.quality_status,
       r.json_content
FROM jd_agent_position_cluster c
JOIN jd_agent_portrait_report r ON r.position_cluster_id = c.id
WHERE c.id = 2
ORDER BY r.created_at DESC
LIMIT 5;
```

两段查询均在测试库实际执行，各返回 1 行。已核对表清单、目录节点总量、任务覆盖和招聘映射分组的汇总数。
