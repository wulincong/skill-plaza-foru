# 岗位画像从哪里查

2026-11-20 使用项目现有只读账号核对 draw.io XML、实时表结构和关联数据。**岗位群画像正文在 `c_industry_chain_position.position_group_portrait`，类型为 `POSITION_GROUP`；具体目录岗位通过 `pid` 找到所属岗位群，再通过 `c_industry_position_ref` 关联企业招聘记录。** 原图没有画出这张招聘映射表。

## 数据位置与实测边界

| 对象 | 表或字段 | 已核验的含义 |
| --- | --- | --- |
| 岗位群画像 | `c_industry_chain_position.position_group_portrait` | LONGTEXT；本次非空值全部为有效 JSON。 |
| 岗位群 | 同表 `industry_chain_position_type='POSITION_GROUP'` | 未删除共 1,421 个，其中 1,396 个画像去空格后非空。 |
| 具体目录岗位 | 同表 `industry_chain_position_type='POSITION'` | 未删除共 3,590 个，自身画像均为空；全部通过 `pid` 连到同产业且未删除的岗位群。 |
| 典型任务、核心技能 | `c_industry_chain_position_typical_task.typical_task/skill_demand` | 通过 `industry_chain_position_id` 连目录节点；样例内容为 JSON 数组，不预设全表格式相同。 |
| 企业招聘映射 | `c_industry_position_ref` | `industry_chain_position_id → 目录岗位.id`，`position_id → c_company_position.id`。 |
| 另一套岗位字典和技能标签 | `c_position_dictionary → c_position_skill_tag` | `position_dictionary_id → 字典.id`；字典 `position_type_id` 指向 `c_position_type`，与产业链目录的 ID 不通用。 |

画像 JSON 样例“机器人研发岗位群”包含 `definition`（定义）、`condition`（任职条件）、`task`（任务）、`skillDemand`（技能）、`basicKnowledge`（基础知识）、`professionKnowledge`（专业知识）、`qualityRequirement`（素质要求）、`dev`（发展路径）、`env`（工作环境）、`taskCourseRecommend`（任务课程推荐）。字段清单来自此样例，不代表全部画像有相同结构。

实测的 65,735 条未删除招聘映射全部连到未删除的 `POSITION` 节点，涉及 740 个目录节点；其中连到 45,260 条不同的当前在招且未删除招聘记录。目录、映射、招聘记录粒度不同，不能将映射行数当岗位数。各条查询独立执行，没有使用同一快照事务。

“聚类后岗位”的生成机制仍未确认。已证实的是岗位群层级和现有映射；本次未查到足以证明算法、聚类批次或生成来源的证据。另一套岗位字典中，1,439 条未删除记录的 `parent_id` 均为 0，`relation_position_names` 均为空，不能靠这两个字段恢复聚类成员。`t_standard_job/t_standard_job_position` 另有标准岗位到招聘记录的映射，但未核实它与画像节点的 ID 关联，不凭同名拼接。

## 进入数据库

在当前项目根目录，优先使用已有工具，内部按进程环境优先、缺项回落 `web/.env` 读取 `MYSQL_*` 配置：

```bash
cd /home/wlc/project/skill-plaza-foru
node scripts/mysql-query.mjs --format table 'SELECT DATABASE(), VERSION()'
```

本机已实测连接到 `ai_crowd_souring_extend`，服务端版本为 MySQL `5.7.43-log`。查询工具支持单条 SELECT/SHOW/DESCRIBE/EXPLAIN；多个查询逐条执行。下面 SQL 可各自保存为一个 `.sql` 文件，再运行：

```bash
node scripts/mysql-query.mjs --format table --max-cell-chars 20000 --file /tmp/portrait.sql
```

该工具默认将每个字段截到 400 个字符。画像需调大 `--max-cell-chars`；数据库查询仍需自行加 `LIMIT`。

需要在 MySQL 终端直接操作时，连接参数取自本机配置。主机、端口和账号可能随部署变化，按本机当前值执行；密码取 `web/.env` 的 `MYSQL_PASSWORD`，在 `-p` 提示中输入，不放在命令行或文档中。

```bash
mysql -h 192.168.8.1 -P 3908 -u tringai_read -p \
  --default-character-set=utf8mb4 ai_crowd_souring_extend
```

进入后执行：

```sql
SET NAMES utf8mb4 COLLATE utf8mb4_general_ci;
```

地址是内网地址，需要从能访问该网段的主机连接。若本机默认客户端报 `mysql_native_password` 插件错误，使用项目查询工具，它会选择兼容客户端。

## 1. 按名称找有画像的岗位群

```sql
SELECT g.id, g.position_name, g.industry_chain_id,
       i.name AS industry_name,
       CHAR_LENGTH(g.position_group_portrait) AS portrait_chars
FROM c_industry_chain_position g
LEFT JOIN c_industry_chain_info i ON i.id = g.industry_chain_id
WHERE g.deleted = 0
  AND g.industry_chain_position_type = 'POSITION_GROUP'
  AND NULLIF(TRIM(g.position_group_portrait), '') IS NOT NULL
  AND g.position_name LIKE '%机器人%'
ORDER BY g.id
LIMIT 20;
```

可将“机器人”替换为目标词，或将名称条件换成已确认的 `g.industry_chain_id`。同名岗位群可能属于不同产业，选择时同时看 ID 和产业。本次查到机器人产业（ID 15）的“机器人研发岗位群”：`646028081372456668`。

## 2. 读一个岗位群的完整画像

```sql
SELECT id, position_name, industry_chain_id,
       position_group_portrait
FROM c_industry_chain_position
WHERE id = 646028081372456668
  AND deleted = 0
  AND industry_chain_position_type = 'POSITION_GROUP';
```

要在 MySQL 终端以 JSON 缩进展示，可选用：

```sql
SELECT JSON_PRETTY(
         CASE WHEN JSON_VALID(position_group_portrait)
              THEN position_group_portrait ELSE NULL END
       ) AS portrait
FROM c_industry_chain_position
WHERE id = 646028081372456668 AND deleted = 0;
```

## 3. 从具体目录岗位找到所属群和画像

```sql
SELECT p.id AS catalog_position_id, p.position_name,
       g.id AS group_id, g.position_name AS group_name,
       g.position_group_portrait
FROM c_industry_chain_position p
JOIN c_industry_chain_position g ON g.id = p.pid
WHERE p.deleted = 0 AND g.deleted = 0
  AND p.industry_chain_position_type = 'POSITION'
  AND g.industry_chain_position_type = 'POSITION_GROUP'
  AND p.position_name LIKE '%机器人算法%'
ORDER BY p.id
LIMIT 20;
```

本次核验：目录岗位“机器人算法工程师”`646028081372456669`，父节点即上述机器人研发岗位群。查群内全部目录岗位可把名称条件换成 `g.id = 646028081372456668`。

## 4. 读目录岗位自己的典型任务和核心技能

```sql
SELECT p.id, p.position_name, t.typical_task, t.skill_demand
FROM c_industry_chain_position p
LEFT JOIN c_industry_chain_position_typical_task t
  ON t.industry_chain_position_id = p.id AND t.deleted = 0
WHERE p.id = 646028081372456669
  AND p.deleted = 0
  AND p.industry_chain_position_type = 'POSITION'
ORDER BY t.id
LIMIT 20;
```

它与岗位群画像是两个粒度：画像由同群岗位共享，任务和技能表按具体节点关联。这里使用 LEFT JOIN，任务未录入时仍能看见目录岗位。

## 5. 从岗位群查它映射的企业招聘记录

```sql
SELECT DISTINCT j.id AS recruitment_id, j.name AS recruitment_name,
       j.education, j.experience, j.min_salary, j.max_salary
FROM c_industry_chain_position g
JOIN c_industry_chain_position p ON p.pid = g.id
JOIN c_industry_position_ref r ON r.industry_chain_position_id = p.id
JOIN c_company_position j ON j.id = r.position_id
WHERE g.id = 698998823548092942
  AND g.deleted = 0 AND p.deleted = 0 AND r.deleted = 0
  AND g.industry_chain_position_type = 'POSITION_GROUP'
  AND p.industry_chain_position_type = 'POSITION'
  AND j.deleted = 0 AND j.publish_state = 'PUBLISHING'
LIMIT 20;
```

本例使用已命中招聘映射的“研发工程与技术开发”岗位群。样例关系为该群 `698998823548092942` → “试剂研发工程师”目录节点 `698998823548092988` → 招聘记录 `473823553777204027`“生物试剂研发工程师”。更换群 ID 即可查其他群。群内不同目录节点可映射同一招聘记录，统计时用 `COUNT(DISTINCT j.id)`。

机器人研发岗位群 `646028081372456668` 本次未命中上述在招映射。这表示本条映射路径下没有满足条件的记录，不能据此推断市场没有相关招聘。

## 6. 6,158 条记录的口径、产业链与学历

2026-11-20 再次只读核验：**6,158 是目录表包含已删除数据的总行数，混合了岗位、岗位群、专业和专业群。** 它不是 6,158 个不同岗位名称，也不能代表所有招聘岗位或整个市场的岗位目录。

| 节点类型 | 含已删除的总行数 | 未删除行数 |
| --- | ---: | ---: |
| `POSITION` 具体岗位 | 3,722 | 3,590 |
| `POSITION_GROUP` 岗位群 | 1,487 | 1,421 |
| `PROFESSION` 专业 | 663 | 622 |
| `PROFESSION_GROUP` 专业群 | 286 | 270 |
| 合计 | 6,158 | 5,903 |

未删除的具体岗位按 `COUNT(DISTINCT NULLIF(TRIM(position_name),''))`、源库排序规则去重，为 **2,713 个名称**。同名岗位可分布在不同产业、不同岗位群中，所以不能将名称当唯一节点 ID。3,590 个具体岗位节点关联到 49 个不同产业 ID，本次全部能连接到产业字典；没有默认过滤产业 `open_status`，其中也包含未开放产业。

查看或导出具体目录岗位及其产业：

```sql
SELECT p.id, p.position_name,
       p.industry_chain_id, i.name AS industry_name,
       i.level AS industry_level, i.open_status,
       p.school_type
FROM c_industry_chain_position p
LEFT JOIN c_industry_chain_info i ON i.id = p.industry_chain_id
WHERE p.deleted = 0
  AND p.industry_chain_position_type = 'POSITION'
ORDER BY p.industry_chain_id, p.position_name, p.id
LIMIT 20;
```

移除 LIMIT 可取得当前全部 3,590 个具体目录节点；项目工具也要相应调大 `--max-rows`，避免输出被裁到默认 200 行。只看某产业时增加 `AND p.industry_chain_id = 15`；只看某岗位名时增加 `AND p.position_name = '机器人算法工程师'`。产业名和产业树层级来自 `c_industry_chain_info`，其中 `level` 不是学历层次；未开放节点要在明确需要时用 `i.open_status=1` 筛选。

**目录适用学校层次与企业招聘学历要求分别读取。** 当前全表 6,158 条记录的 `school_type` 均为 NULL，不能据此识别中职、高职或本科适用层次；3,590 个具体岗位通过业务流程表 `c_industry_chain_full_link` 能连接到的未删除流程，其 `school_type` 也都为空，另有 200 个岗位未命中未删除流程。具体岗位和岗位群中 `profession_library_id` 没有正值，不能直接用这个字段补齐它们的学历。画像 `condition` 中的学历文字属于存储的画像建议，未经来源核实不作为企业招聘学历的实测统计。

企业招聘要求读取 `c_company_position.education`，经目录岗位映射查询。例如统计上文“研发工程与技术开发”岗位群：

```sql
SELECT j.education, COUNT(DISTINCT j.id) AS job_count
FROM c_industry_chain_position g
JOIN c_industry_chain_position p ON p.pid = g.id
JOIN c_industry_position_ref r ON r.industry_chain_position_id = p.id
JOIN c_company_position j ON j.id = r.position_id
WHERE g.id = 698998823548092942
  AND g.deleted = 0 AND p.deleted = 0 AND r.deleted = 0
  AND g.industry_chain_position_type = 'POSITION_GROUP'
  AND p.industry_chain_position_type = 'POSITION'
  AND j.deleted = 0 AND j.publish_state = 'PUBLISHING'
GROUP BY j.education
ORDER BY job_count DESC;
```

改为具体岗位查询时，将 `g.id = ...` 换成 `p.id = ...`，其余条件保留。本例实测本科 270、硕士 164、大专 46、博士 30、初中及以下 23、中专/中技 3、不限 2、高中 1，共 539 条不同在招记录；仅代表此映射样本，不能外推到整个产业或市场。

学历代码沿用项目 `scripts/talent-data/core.mjs`：`BENKE` 本科、`SHUOSHI` 硕士、`BOSHI` 博士、`DAZHUAN` 大专、`GAOZHI` 高职、`ZHONGZHUAN/ZHONGJI` 中专/中技、`GAOZHONG` 高中、`CHUZHONGJIYIXIA` 初中及以下、`BUXIAN` 学历不限。缺失和未知枚举单独保留，不转换成不限，也不按学历标签直接判断可录用。

## 验证与使用限制

- 证据来自结构图、`information_schema.COLUMNS/STATISTICS`、画像分类型计数、父子关系连接、JSON 有效性与键名检查、招聘映射分组和有限样例查询；均为只读。上述 1–5 的查询及 JSON 缩进表达式已通过真实库执行，具体返回规模会随数据变化。
- 第 6 节的节点类型总数、名称去重、产业连接覆盖、目录/流程学校类型空值和招聘学历分布均通过真实库核验；本节两条示例 SQL 另经逐条执行通过。目录学历适用层次仍缺结构化证据，不通过名称、画像文字或招聘学历自动回填。
- 元数据检查时，目录、典型任务、映射、岗位字典与技能标签这五张表均只有主键索引；带 `LIMIT` 的映射查询仍可能扫描映射表。大范围查询前先 EXPLAIN；本次映射连接计划从映射表扫描并对目录和招聘表作主键连接，没有扫描招聘主表全量正文。
- 当前公共 `talent-data-query` 接口提供目录检索和招聘统计，没有提供画像正文、典型任务或按目录节点精确筛选招聘记录的接口。这里的原始 SQL 是开发查询方法，不能据此声称在线能力已经接入。
- 画像的生成方法、来源、更新时间和业务质量尚未确认；存储的画像、技能标签分值与招聘原文统计须分别解释。尚未证明的算法生成关系不写入结构图。
