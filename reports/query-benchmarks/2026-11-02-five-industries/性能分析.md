# 查询耗时汇总与提速分析

本页根据同目录 results.json 的 20 次成功实时请求计算。它们是不同筛选条件的单次观测，不是同一查询的延迟分布或性能承诺。

| 项目 | 结果 |
|---|---:|
| 平均完整请求耗时 | 75.938 秒 |
| 最长：Q17，生物医药全国在招岗位数 | 99.322 秒 |
| 最短：Q12，深圳低空经济应届/在校经验岗位数 | 41.754 秒 |
| 平均数据库连接/SQL批次耗时 | 75.731 秒 |
| 批次耗时占完整请求耗时 | 99.728% |
| 平均批次之外的耗时 | 0.206 秒 |

完整请求计时包含 CLI 启动、解析、等待、建连、统计、传输、校验和落盘。sqlBatchMs 包含连接/传输，不等于纯服务端 SQL 时间；没有 CPU/IO 或锁等待的实测分解。

## 已确认的执行路径与额外工作

- 当前编译器即使只请求 positions.count，也在 scripts/talent-data/compile.mjs:31–34 计算 MAX(update_time)、企业与地址缺失量、城市/省份/岗位名/来源缺失量，并始终关联地址表。全国纯计数本身不需要这些额外输出。正式改造须同步调整结果的可用元数据与校验，不能删除 SQL 列后仍声称原完整性检查有效。
- 对原 Q17 的只读 EXPLAIN：岗位表从 publish_state_index 开始，估计 6,982,802 行；逐条主键关联地址，再用相关子查询检查产业关联。估计行数不等于实际扫描量。
- 对产业优先候选改写的只读 EXPLAIN：先对产业关联 chain_id 索引做范围检索（估计 584,323 行），去重 position_id 后约 292,161 个候选，再按岗位主键关联。在此案例中减少了从大范围在招岗位出发的访问；仍有派生表去重成本。
- 当前已存在 (industry_chain_id,position_id) 等产业关系索引；岗位表未发现以 company_address_id 为首列的索引。不能仅凭字段名就断言新增某个索引一定有效。

## 只读改写验证

对生物医药全国在招数量，采用同一产业子树、在招/删除条件；先筛产业关联、DISTINCT position_id 去重，再主键关联岗位，仅计算 COUNT(*)，移除地址关联与额外统计。

| 项目 | 原基准 Q17 | 改写试跑 |
|---|---:|---:|
| 岗位记录数 | 273,360 | 273,360 |
| 完整命令耗时 | 99.322 秒 | 7.442 秒 |

本次观测约快 13.35 倍，耗时减少 92.51%。实际 SQL、执行时刻与结果见 [optimization-probe.json](optimization-probe.json)。原基准和试跑不是同一事务，未控制数据库缓冲池状态，调用路径的包装也不同；只验证该案例的数量相同和改写可执行，不把比例外推到其余 19 条，也不代表已接入 Skill。

## 建议实施顺序

1. 纯计数按需编译最小字段；没有地域过滤且不要求地址质量指标时，省略地址关联。昂贵的源最大更新时间/缺失统计独立成可选能力，执行读取时间仍如实保留。
2. 对产业选择性较好的请求，评估产业候选集合优先；按岗位 ID 去重后再关联主表。城市或其他维度更有选择性时，以实际计划和测量选择入口，不对所有查询强制同一顺序。
3. 同一产业四个条件用一次条件聚合复用候选集合，使这组 20 个业务答案有机会由 5 次聚合产生。必须完整保留省/市别名、学历和经验条件、缺失地址规则，以及各组独立分母；当前把四组放到同一请求仍会生成四个 base SQL，不能称为已合并扫描。
4. 普通重复查询使用已实现的 15 分钟结果缓存；live 仍访问数据库。缓存只能加快重复读取，不替代首次查询优化，也不冒充数据源实时更新。
5. 在上述改写后再评估覆盖索引：产业关系 (industry_chain_id,deleted,position_id)，以及地址优先路径可能需要的岗位 (company_address_id,publish_state,deleted)。现有索引能否复用、读写成本与计划变化都要独立测试；本轮没有 DDL 或索引修改。
6. 高频固定统计可进入定时预聚合层，明确更新时间，并正确处理下架、删除、地域变化和一岗多产业。任意关键词/未覆盖维度仍走受控明细查询。

后续正式接入时保留当前基准作为对照，以同口径验证全部 20 个结果、地域缺失、空结果、跨产业重叠和部分失败，再记录新的整轮耗时。当前仅分析和 SELECT/EXPLAIN 试跑，没有修改查询引擎代码或数据库结构。
