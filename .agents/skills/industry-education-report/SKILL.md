# 产教决策报告

**交付目标。** 生成完整报告，最终通过 [report-rendering](../report-rendering/SKILL.md) 交付可打开的网页，同时保留正文、结构化报告、结构验收和证据复核四份文件。不提供简报/完整版选择，不以聊天摘要或业务 build 完成代替最终交付。关键问题等待用户时先停在询问，得到回复后继续下面的流程。

## 执行流程

按编号顺序执行，每步写明输入、动作和输出，前一步的输出是后一步的输入；需要回退时只按文中写明的回到点回退。

1. **明确决定与范围。** 输入：任务原话。动作：提取读者、决定、对象、地域和时期，采用已明确的信息；会改变取证方向的歧义先询问；“学院”不能自动解释为“高职”，不猜办学层次、预算、容量或决策偏好；缺城市而本校材料已够用时采用“本校”；仅问数量、薪酬等统计时交由 [talent-data-query](../talent-data-query/SKILL.md) 回答。输出：决策问题与范围（后续写入 report.json 的 decision 与顶层字段）。

2. **制定取证与呈现计划。** 输入：决策问题与范围。动作：先读[报告契约](references/data-contract.md)，列出要验证的判断；再按[呈现计划约定](references/presentation-plan.md)在工作区起草 `presentation-plan.md`，为每个预期可视化数据关系写清要回答的问题、数据关系、候选图型、所需数据形式（完整分组 rows、对比组、配对列、时间序列）和来源，呈现计划反过来确定取数请求需要哪些维度与 cohort。输出：`presentation-plan.md`（工作区工件）。

3. **受管取数。** 输入：呈现计划与取证清单。动作：查询全部遵循 talent-data-query——在线用 `talent_query` 提交地域、产业名称、真实筛选和所需指标，`talent_inspect` 核验已有结果；不自行写查询 JSON、SQL 或连接脚本，不执行 query/plan CLI，不套 timeout 或选择计划；整个产业交给查询技能解析，不能替换成名称关键词；无原生工具时先读查询技能按其入口执行；优先复用同会话、同范围、同口径的已核工件，缺指标或明确刷新才取数。完整分析覆盖范围、需求、门槛与薪酬、任务与培养定位、实施条件、备选方案、行动及风险；与当前决定无关的专题说明原因，不硬凑统计；岗位需求与本校能否实施分别核验；用户粘贴的原句就是材料，引用实际段落即可，授权附件或知识库回查原文；用户限定来源时遵守，不自行扩地区、换样本或改时间窗；仅复现广东历史口径时才读取 [05 快照](references/05-数据库字段摸底与口径.md)。取数后对照呈现计划核对数据形式：计划所需的分布、对比组等维度缺失即取数不充分，回到第 2 步修订计划并补查；确实无维度可补时转入第 4 步询问用户。输出：已核查询工件（data/tq-…/result.json）与材料清单。

4. **需要人判断时询问。** 输入：范围含糊、关键证据缺失、来源冲突会改变结论，或备选方案涉及用户未给出的预算/优先级。动作：说清已知、缺口和各选项影响，问一个可回答的问题；证据缺口提供“补充材料”“扩大范围”“按现有证据继续”，扩围选项写明建议范围，未明确范围先问清；支持决策卡时用单选或输入卡，普通文本入口列同样问题；结束本轮等待真实回复，不同时构建或交付终稿；查询失败按查询技能状态停止，不自选降级方案重试；补证或扩围后回到第 2 步重新评估；“扩大范围”“请生成”、沉默都不等于允许带缺口交付；仅用户明确选择按现有证据继续，才记录原话（continue_quote）并把受影响决定保留为未决；若必要条件已有证据否决，可直接形成暂缓或否定意见；次要缺项就地说明，不反复追问无关材料。输出：用户真实回复或明确的取证授权。

5. **撰写完整报告。** 输入：已核工件、材料与用户回复。动作：统一 `edition=full`，按[章节表](assets/templates.json)和报告契约组织；全文总分总——开篇先回答核心问题，中段逐项论证，末尾收束到建议、条件与未决项；每个论证段同样总分总——段首给判断，中段给具体依据和决策含义，段末收束到对当前决定的影响；方案比较包含可行替代路径或暂缓方案，建议是研究结论，不能写成用户已批准；所有用于判断的分布、薪酬、岗位等数据完整绑定交接，不只保留总量；用户材料的量化事实也登记 metrics 并被 claim 引用，同口径数值保持单位与统计对象一致；缺少联合分布或时间序列时不能拼造交叉关系或趋势；校验出错修正字段及引用，不删掉已有论证以求过关。输出：report.json 草稿。

6. **业务复核。** 输入：report.json 草稿与呈现计划。动作：内容修订先复制已审稿为工作草稿，保留 output/report-* 原件及指纹；草稿、review.md 和命令都在当前会话工作区，技能脚本用绝对路径，不 cd 到技能安装目录；先运行 `python3 <技能目录>/scripts/report.py preview report.json`；按原材料逐条核对 claim 的含义、metric 绑定、单位/分母、推断和限制；检查各章是否回答不同问题、实施条件是否被需求总量冒充、F08 是否包含责任方/下一步/条件/核验办法；逐项核对呈现计划——每个计划图表所需的数据字段在实际保留的工件中存在且口径一致，发现缺口回第 2/3 步补齐后重新复核。输出：review.md，记录审核者、日期、每条 claim 的依据与审核理由、范围/需求/可行性检查结果和呈现计划核对结果。

7. **业务构建。** 输入：复核通过的 report.json 与 review.md。动作：运行 `python3 <技能目录>/scripts/report.py build report.json --review review.md`。输出：output/report-* 四份原件（正文、结构化报告、结构验收、证据复核）。build 成功只代表业务交接完成，不是最终交付。

8. **交接渲染与最终验收。** 输入：本轮 build 输出目录。动作：立即读取 report-rendering，把正文、report.json 和 `presentation-plan.md` 一起交给它，沿用已核结论、完整指标、来源和未决项，并明确最低呈现要求——正文以 report.md 的成段散文为准、不得按 claim 字段重排为标签条目，支持核心判断的可比数据关系尽量成图、整份报告至少 2 种图型、同一图型不超过 3 张；渲染完成后按[验收清单](references/acceptance.md)核对实际网页，不满足项先要求渲染修订；只有平台产生真实网页入口并通过验收才算交付成功，未成功时说明停在哪一步并保留工件，不能声称已交付。纯呈现修订复用已核业务版本，按渲染技能重新登记新版本。最终回复简述结论和未决项，使用平台生成的网页及下载入口；不列工作区路径、内部字段或工具验证过程。输出：已交付的报告网页与下载入口。

## 验收标准

四类标准在交付前逐条核对，完整清单见[验收清单](references/acceptance.md)；任何一类不通过都不得声称已交付。

- **证据与结构**（report.py 自动校验）：preview/build 通过，绑定指纹一致，F08 行动四字段齐全，evidence_checks 按 scope/demand/feasibility 排列。
- **呈现**（对最终网页人工核对）：支持核心判断的可比数据关系成图或给出数值表与具体理由，不能只剩总量卡片；整份报告至少 2 种图型，同一图型最多 3 张，换方向或配色不算新图型；图型按数据关系选择，只支撑单一关系视为取数不充分，回流程补维度；图注含来源、单位、分母和展示范围，无时间序列不画趋势，同一对象跨图名称、颜色、单位一致。
- **文风**：全文总分总，开篇回答问题、末尾收束到建议与未决项；每个论证段段首判断、中段证据、段末收束到决定；判断不在段首、段末和篇末重复表述。
- **交付**：平台产生真实网页入口，打开实际网页核对全文、图表、数值表和来源；不以构建日志或工作区文件代替成品核对。
