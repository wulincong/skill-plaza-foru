# 呈现计划约定

呈现计划（工作区 `presentation-plan.md`）把“这部分数据将来怎么呈现”提前到取数阶段：先确定每个预期图表所需的数据形式，再据此发起查询，保证交给渲染技能的数据拿过来就能画，不出现“取了数但只交接四个总量”的缺口。

## 何时写与修订

- 执行流程第 2 步起草，随取证进展和用户补充材料修订；第 6 步业务复核时逐项核对；第 8 步随正文和 report.json 一起交给 report-rendering。
- 计划是工作区工件，不进 report.json 的 schema，由 report.py 之外的流程（review.md 记录）人工核对。

## 每项内容

每个预期可视化关系登记一项：

| 字段 | 说明 |
| --- | --- |
| id | 计划内唯一编号，如 P-DEGREE |
| 问题 | 这张图要回答的具体问题，如“学历门槛集中在哪一档” |
| 章节 | 支撑的章节（F01–F09）与判断主题 |
| 数据关系 | 比较 / 构成 / 分布 / 关联 / 趋势 / 变化 / 区间 / 矩阵 / 地域，对齐 report-rendering [图表选型](../../report-rendering/references/chart-selection.md)的关系分类 |
| 候选图型 | 按关系给出的图型，如柱状图、堆叠柱、点分布、分省地图；实际可执行图型以渲染技能和 chart-visualization 当前能力为准 |
| 所需数据形式 | 画这张图必须拿到的最小字段：分组行表（label/count/share 与分母）、对比组（同口径 cohort）、配对列（对象×两列数值）、时间序列（多期观测）等 |
| 来源 | talent_query 请求中的 cohort 与指标，或用户材料、知识库 |
| 状态 | 已取 / 待取 / 不可得（写明理由与影响） |

## 如何驱动取数

- “所需数据形式”直接翻译成取数请求：分组行表对应分布指标；对比组对应同一请求内的多个 cohort（同一产业的地域、学历、经验等对比尽量合并到一次请求）；时间序列对应多期口径；仅用户限定单点时保留快照。
- 最低呈现要求在计划层面就要满足：预期图表整体至少覆盖 2 种数据关系（对应至少 2 种图型），同一图型计划不超过 3 张。取证后对照发现只支撑一种关系时，视为取数不充分——先回到计划补维度（如增加学历、经验、薪酬分位、地域对比、岗位构成），确实无维度可补时按执行流程第 4 步询问用户。
- 不为凑图型伪造关系：没有时间序列不计划趋势图，只有边际分布不计划交叉矩阵。数据确实只够一种关系时走上一条的补维度或询问路径，不在计划里硬凑。

## 交接与边界

- build 后把 `presentation-plan.md` 与正文、report.json 一起交给 report-rendering；渲染按计划的数据关系选型执行，实际图型可以比计划更适切，但不得低于最低呈现要求（至少 2 种图型、同一图型最多 3 张、支持核心判断的可比关系成图或注明理由）。
- 计划只约束数据形式与多样性下限，不规定页面结构、布局和主题——那是渲染技能的职责；它也不是 report.json 中被移除的页面 charts 规格的回归。
