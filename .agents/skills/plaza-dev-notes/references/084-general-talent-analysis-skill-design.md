## 动机

用户在 083 审查后询问真实数据库是否可连，并希望按提示词分析不同地域、行业、院校专业和岗位。现有 wechat-report 把广东 AI 的筛选、结论和公众号排版耦合在一起；仅修改提示词无法纠正数据范围错误和缺失的证据绑定。需要一套可以复用的查询与指标流程，再由技能组织分析和选择交付形式。

本记录是本轮方案建议，不表示用户已要求批量实施、注册新技能卡片或修改数据库。当前技能代码及用户已有的 brand.json 修改保持原样。

## 当前已验证的接入点与事实

- `scripts/mysql-query.mjs:70` 从进程环境及 `web/.env` 内部读取配置；通过它执行 `SELECT 1, VERSION(), NOW()` 成功，服务器为 **5.7.43-log**，连接探针耗时 **53ms**。只取三行岗位名称/学历/经验也成功；这些样本不用于推断任何岗位分布。
- wechat-report 安装目录下 `.venv/bin/python -B` 使用 PyMySQL，在临时进程内部读取同一配置执行 `SELECT 1, VERSION()` 成功。未写出、复制或回显凭据。技能根目录和 scripts/ 均不存在 `db_config.json`；因此“主机及依赖可连”和“原 fetch_data 默认入口已配置”是不同结论。
- 对岗位表的 update_time 索引进行了只读检查后，按该索引读取最大更新时间，值为 **2026-10-31 14:53:36**（数据库存储值，未转换时区）。这是平台记录更新时间；不是职位真实发布时间，也不是所有切片均更新到该时点的证明。不能因为查询发生在今天，就把数据称为今日市场全量。
- `scripts/career-market-query.mjs:14` 当前仅有七类白名单查询；`:44` 起参数校验仍默认广州、Java 及后端等岗位词，不能原样充当通用查询引擎。`web/server/index.ts:130` 起给在线 Agent 注入的也是这组白名单；新增能力必须同时处理受信工具入口与运行时声明，不能让用户会话自行读取项目 `.env` 或任意工程源码。
- `information_schema.COLUMNS` 已确认以下表与关联字段；这些是当前真实结构，全部映射内容的质量仍待单独验证：

| 维度 | 已确认的数据结构 | 使用边界 |
|---|---|---|
| 地域 | `c_company_position.company_address_id → c_company_address.id`；地址含 province/city | 来自企业关联地址，不自动等同真实工作地；地址缺失不得悄悄从基数消失 |
| 产业 | `c_position_chain.position_id → c_company_position.id`；industry_chain_id → `c_industry_chain_info.id`，字典含 name/pid/level | 多对多映射，需固定层级与去重岗位计数；不能与岗位类型树的“人工智能”ID 混用 |
| 专业 | `c_professional_library` 含 id/code/name/school_type/level；`c_professional_position_relation.professional_id → 专业 id`、position_type_id → `c_position_type.id` | relation.status 注释明确 0 无效、1 有效；同名专业跨学制或存在产业链扩展条目，不能只凭名称选第一个 |
| 岗位 | `c_position_type` 字典与主表 position_type（varchar）、name | 岗位类型、名称关键词检索口径分别记录，关键词不能静默替代类目；需验证 ID 串格式与缺失覆盖 |

- 小样本实测：高职“软件技术” `id=1822`、`code=510203`、`school_type=VOCATIONAL_TECHNICAL_COLLEGE`，通过 relation 关联到 Java、C/C++、PHP、Python、C# 五个返回项，status 均为 1。这是现存映射的有限样本，不是全部关联清单，不证明企业在 JD 中要求该专业，也不支持就业率/就业结果结论。
- 产业树中当前 level=0 的有限样本：机器人 id=15、软件和信创 id=24、人工智能 id=26、新能源产业 id=44。这些 ID 属于产业链字典；旧 wechat-report 默认 1242 属于岗位类型字典，禁止跨字典复用 ID。
- 另有 `c_major_match_analysis`（含 match_percentage/requ_quantity/salary_range 等字段）、`c_industry_major` 等派生分析表。其生成方法与新鲜度未查验，不因字段名包含“匹配率/需求数量”就把存储结果当作可直接发布的实测指标。

## 建议约定与数据协议（候选，待实现）

### 1. 保留对话入口，抽出共享数据能力

处理链：用户问题 → 结构化分析规格 → 数据字典解析 → 统一样本条件 → 聚合与校验 → 有证据的分析 → 对话/报告/公众号输出。

- 模型负责意图理解、同义词候选、选择分析角度、解释与建议；程序负责真实查询、集合过滤、数值计算、单位/分母、指纹及验收。查询失败或数据不足时如实报告，不能切换到演示数据或模型常识补数字。
- 建议把通用数据能力做成受信工具，后续可供其他技能复用；wechat-report 保留现有入口，负责选择公众号交付。当前不用新建卡片、迁移其他技能或改变原有表单行为。
- 复用已有连接配置、客户端选择与受控执行机制，不为每个技能另存一套密码。现有 career-market-query 调用保持兼容；新增规格通过新入口或显式版本扩展，具体文件和驱动封装待实现时确定，不能把本记录的候选接口当现有 API。

### 2. 先固化问题与样本，避免隐含默认值

建议 `analysis-spec/1` 至少包含：

```json
{
  "schema": "analysis-spec/1",
  "question": "比较广州与佛山高职软件技术专业相关岗位的学历和薪酬结构",
  "regions": [
    {"level": "city", "province": "广东省", "name": "广州市"},
    {"level": "city", "province": "广东省", "name": "佛山市"}
  ],
  "industries": [],
  "majors": [{"id": 1822, "code": "510203", "schoolType": "VOCATIONAL_TECHNICAL_COLLEGE"}],
  "roles": [],
  "cohort": {"state": "publishing", "timeBasis": "current_database_snapshot"},
  "groupBy": ["city"],
  "metrics": ["education_distribution", "salary_distribution", "salary_quantiles"],
  "output": {"format": "chat", "audience": "college"}
}
```

上例 ID 为有限实查样本，其余为建议字段，不代表 schema 已发布。`current_database_snapshot` 表示执行时读取库内可用记录，不承诺市场实时更新。

- 未指定行业不自动添加 AI 条件，未指定地域不自动落到广东；必要范围根据问题明确声明，影响结果的歧义才追问。专业同名时结合学校层次/代码确定；不能把技校、高职和本科同名专业混作一项。
- 不同维度默认 AND，同一维度多选默认 OR；比较任务建立分组样本及各自分母，不把两个地区混成一份总量。提示词要求的 OR、排除、交叉比较要显式表达，不硬套默认。
- 地名/行业/专业/岗位先解析为字典候选与可追溯 ID。不存在匹配时报告未识别；名称关键词兜底必须标明“名称包含”并记录条件，不能伪称完整产业样本，也不能无声扩大范围。
- “近一年”只能匹配已验证的时间语义。update_time 窗口可明确称为平台更新时间筛选；没有真实发布时间或独立多期快照，不报告“新增招聘/同比增长/招聘趋势”。

### 3. 用同一份规格生成所有查询

- 受信工具接受允许的字段、运算符、聚合及普通参数，由编译器生成参数化 SQL；不向在线 Agent 开放任意原始 SQL。按实际 MySQL 5.7 能力实现层级解析，不设计成依赖 8.x 递归语法的查询。
- 行业子树在小字典中解析；岗位集合按 `position.id` 去重。关系筛选优先考虑 EXISTS 或预先去重的候选集合，避免多产业链/多专业关联使岗位数膨胀；跨行业/跨专业比较明确集合可能重叠，占比不能默认相加。
- 采用统一的在招/删除过滤、地址缺失处理、薪资有效规则、岗位计数单位与固定截止时间；聚合共用同一 cohort 指纹。需要一致快照时在同一受控只读事务中执行，执行时间与源数据更新时间分别记录。
- 常规学历、经验、地域、岗位、薪资分布先在库端聚合；涉及分位数可使用受限的数值频数分布计算，明确精度与算法。能力词分析只对范围已限定的数据分批处理，区分全量结果和抽样结果，不把样本占比包装成全量实测。
- 大范围先 EXPLAIN、设单查询和总预算；重查询串行，复用已有最多并发 2 的轻查询约束。当前返回行数上限不等于数据库扫描上限；不得默认 fetchall 全库岗位描述。

### 4. 指标、结论与图表显式绑定

建议每个指标至少记录 `metricId/cohortId/queryId/value/unit/numerator/denominator/validN/missingN/method/executedAt/sourceFreshness/evidenceClass`；查询日志保留实际 SQL/参数、耗时、结果及 hash，内部保存。

- 事实类结论引用 metricId，图表引用相同指标；验证字段绑定和计算式，不能再检查“数字是否出现在全局数字池”。内部的去重岗位记录数可以用作核查基数，对用户须明确是库内样本，不能外推区域市场岗位总量或招聘人数。
- `evidenceClass` 至少区分库内统计、库内关联/规则映射、分析推断；专业相关岗位来自映射，不等同企业明确要求专业或毕业生就业去向。缺少就业跟踪数据时不计算就业率；缺少验证方法时不发布“专业匹配率”。
- 校验分数据/大纲预检与渲染后验收。缺数据、空检查、缺图片、旧 manifest、指纹不一致都不能显示完整 PASS。预检通过不等于成品可交付。
- 分析结构随问题和可用证据选择：单城不画城市排名；少类别不用固定“四大赛道”；空结果/低有效薪资不输出固定薪酬结论；横截面不输出动态趋势。

### 5. 输出与数据职责分离

- 简单问题直接返回数据表和解释；比较任务按同口径并排输出；完整研究报告组合适用章节；公众号交付复用已有版式/图表/主题资产，再修复 083 已复现的高度、缺图验收及打包缺陷。
- 正式公众号大纲与推送沿用已授权流程；不把普通问答强制变成整套长图和多轮确认。微信上传仍须用户明确要求，配置和 SQL 不进入公开产物。
- 用户产物与内部证据分开；ZIP 只采用本次工件清单，下载链接只有实际服务路由支持后才输出。当前没有新增图片/ZIP 下载 API。

## 成本与取舍

- 否决只扩写 SKILL.md 或用更多固定行业模板：实际筛选、去重与指标错误仍会存在，模板量越大维护越难。采用少量稳定的数据/证据接口配合模型自适应组织，代价是先建设查询与验证层。
- 否决直接让模型任意拼 SQL：容易把行业、专业、岗位和更新时间的语义混淆，也难约束成本。采用可扩展的结构化规格与指标注册表；遇到不支持的新指标诚实说明，需要新增实现后再回答，不凭空声称“任意问题都支持”。
- 否决只靠专业名 LIKE 搜岗位：会丢失现有专业—岗位映射，并把“读什么专业”与“岗位名称”混淆。优先库内有效映射；代价是要核验覆盖率、准确率和学制维度。规则补充或模型推断可以作为明确标注的候选，不能冒充库内事实。
- 不修改源数据库、不直接建索引或另建全量复制库。先利用现有索引与聚合；慢查询和模糊岗位检索的中文召回问题沿 017 另行评估。此方案尚未做全量性能验收。
