## 目标与现状

用户在同一浏览器登录优才知路或广场后，打开另一站的个人工作区应能直接继续。建议让广场成为优才现有统一认证中心的一项独立应用。账号、登录方式和统一登录态由认证中心管理，两站各自建立业务会话，各自决定用户能操作哪些资源。

## 两个方向怎样打通

1. 用户先到**官网**。官网跳转统一中心，用户完成一次验证。随后打开广场的“我的任务”或 T03 工作区，广场将浏览器顶层跳转到同一中心。中心认可已有会话，签发专供广场使用的短时一次性票据。广场后端验票，建立本地会话，带用户回到原任务。
2. 用户先到**广场**。广场的登录按钮直接进入同一中心。完成验证后打开官网工作台，官网通过自己的应用登记取得自己的票据，进入该用户的工作台。两站可以有不同域名，每个站点只使用自己签发的业务会话 Cookie。后续平台也按各自的应用登记和回调接入。
3. **首页也要自动显示用户时**，优先在已有门户和广场的受保护入口触发上述跳转。对于允许匿名的首页，若要一打开就显示头像，两站各执行一次中心支持的免交互检查。已有中心会话就建立本地会话，没有就回到访客页，并避免循环重定向。标准 CAS 提供 `gateway` 语义，现网是否有等价参数待联调。如果旧门户会话仍有效但中心会话已过期，安排一次中心登录以建立新的统一登录态。[CAS 协议](https://apereo.github.io/cas/7.3.x/protocol/CAS-Protocol-Specification.html)

## 广场端接口与数据

| 拟建接口 | 服务端职责 |
| --- | --- |
| `GET /auth/login` | 发起短时登录事务，保存允许的站内返回路径，向固定 HTTPS 中心发起顶层跳转。回调使用已登记的服务端路由，前端 hash 地址只作为回站后的目的地 |
| `GET /auth/callback` | 按联调契约将 `st` 交给受信后端验票，绑定发起登录的浏览器事务。要求票据签给广场、短时有效且只能消费一次。以可信响应中的账号标识及有效状态建立会话，然后跳至去除票据的站内路径 |
| `GET /api/me` | 根据本地服务端会话返回当前用户与广场内权限。Vue 刷新或换页用它恢复头像和身份；业务请求由后端重新判定权限 |
| `POST /auth/logout`、拟议 `/auth/slo` | 用户发起全平台退出时清除广场会话并转至中心退出。按中心约定接收并认证退出通知，用上游会话标识或其票据关联撤销对应会话。重复通知应能安全处理。账号停用通过平台事件或有时限的重新校验生效 |

广场只需本地用户映射 `principal(id, issuer, union_id)`，其中 `(issuer, union_id)` 唯一，生产和测试使用不同身份命名空间。如果验票响应只返回门户内部 ID，由认证方提供服务端映射取得统一标识。会话保存随机令牌摘要、`principal_id`、有效期和可供退出关联的标识。浏览器只持有广场域自己的 `HttpOnly; Secure; SameSite=Lax` Cookie。与认证方确定登录事务绑定方式，例如原样回传由广场生成并与浏览器绑定的随机标记。认证中心专用应用凭据只配置给广场后端。日志省略票据、Cookie 和令牌，Pi 与 gVisor 任务只接收本地任务身份。

新任务、会话、附件和交付物由后端从当前会话写入 `ownerId = principal.id`。对列表、详情、SSE、上传、暂停、续跑、下载均检查归属。组织协作由显式授权控制，外部 API 调用使用独立服务身份和授权范围。个人下载与主动发布的分享链接走各自权限。上线新入口前一并核对早于普通路由处理的交付入口 `web/server/index.ts:287`。旧演示手机号与共享记录缺少可信归属，保存在内部历史区，有可靠归属证据才迁入个人空间。后台运营权限单独授予。[129 多用户任务验收](129-sandbox-v2-greenfield-migration.md)

## 接入顺序与放行条件

| 顺序 | 交付 | 放行条件 |
| --- | --- | --- |
| 1. 与认证方登记测试应用 | 确定广场测试 HTTPS 域名、精确回调、验票接口及调用凭据、稳定用户字段、退出通知和禁用语义 | 测试账号在广场回调得到一张票据，广场后端独立验票得到可验证的 `union_id`。过期、重复使用或签给其他应用的票据均被拒绝 |
| 2. 建立最小登录闭环 | 接入登录、回调、本地会话、当前用户和退出。门户与广场配置同一环境的中心，在受保护入口自动发起登录 | 两个干净浏览器环境分别验证“官网先登”和“广场先登”，每个方向只输入一次凭据。两端确认同一测试账号，直接访问第二站的工作区无第二次登录操作 |
| 3. 接入 T03 及私有资源 | 将已验证身份传给任务 API，补齐文件、事件与历史的所有者授权 | 用测试账号 A、B 验证各自历史和任务。同一账号换浏览器登录可恢复自己的任务，B 无法读取、续跑或下载 A 的私有资源；已明确公开的作品按分享策略访问 |
| 4. 灰度正式流量 | 另行登记生产应用、核对两站规范域名，在邀请账号中验证登出与失效 | 从任一站发起统一退出后，两站已有的私有页面再次请求都要求登录。停用、切换账号及中心不可用时行为符合约定。故障时关闭广场新增受保护入口，门户可继续运行 |

第一步需要认证平台维护方提供测试应用登记、正式契约和两个普通测试账号。无需导出用户或密码。认证库管理员凭据用于本次只读核对，业务服务和沙箱均无需获得该凭据。

## 成本与取舍

复用既有 CAS 中心，改造集中在广场后端、资源归属和门户首次访问行为。代价是依赖现有中心的可用性、主体字段和通知能力；这些需要实际联调。直接共用用户表只能复用账号资料，不能让浏览器复用登录态。扩大发 Cookie 的域范围也覆盖不了不同注册域，并会扩大凭据的可见范围。另建身份中心会增加账号关联与会话迁移成本。若将来要接只支持 OpenID Connect 的平台，可在同一身份源上增加协议适配，沿用稳定用户映射。
