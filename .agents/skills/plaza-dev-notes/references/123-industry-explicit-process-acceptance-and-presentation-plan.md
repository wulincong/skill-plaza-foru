# 123 · 产教报告编号流程、取数前置呈现计划与验收硬约束

**状态：已实现（文档约定层）。** 技能指引、呈现计划与验收清单落地；report.py、report.json schema、report-rendering 与平台检查未改动。真实端到端一轮报告的复验**待验证**。

## 动机

用户指出产教 SKILL.md 的流程与验收不够明确：顺序隐含在段落式加粗标题里，没有编号和每步输入输出，验收散落且多为原则表述。同时要求把呈现决策前移——取数阶段就确定数据呈现方式，据此确定交给渲染技能前的数据形式；并提出验收硬约束：图表尽可能丰富、至少 2 种图型、同一图型不超过 3 张、总分总既是全文也是每个论证段的标准。115 记录的真实教训（取数后有分布数据、交接只剩四个标量、页面只有文字和指标卡）正是呈现后置的后果。

## 约定细节

- `.agents/skills/industry-education-report/SKILL.md:10` 起执行流程改为 8 个编号步骤，每步固定“输入→动作→输出”，前一步输出是后一步输入；`:30` 起验收标准分四类并指向验收清单。原有行为约束（受管取数边界、询问三选项、continue_quote、build 门槛、交付判定）全部保留，只是重新编组。
- 新增 `references/presentation-plan.md`：流程第 2 步（`SKILL.md:16`）取证前起草工作区 `presentation-plan.md`，每项登记 id、要回答的问题、支撑章节、数据关系（对齐 report-rendering chart-selection 关系分类）、候选图型、所需数据形式（分组 rows/对比组/配对列/时间序列）、来源与状态；“所需数据形式”直接翻译成取数请求的 cohort 组合与指标（`SKILL.md:18` 取数后对照核对），第 8 步随正文和 report.json 一起交给渲染（`SKILL.md:28`）。
- 新增 `references/acceptance.md`：四类可勾选清单——证据与结构（report.py 自动项）、呈现（丰富度 + 多样性硬约束 + 图表质量）、文风（全文与每段总分总）、交付（平台真实入口 + 成品核对）。
- 硬约束三条：支持核心判断的可比关系成图或给出数值表与具体理由；整份报告 ≥2 种图型且同一图型 ≤3 张（换方向/配色不算新图型）；数据只支撑单一关系视为**取数不充分**，回流程第 2/3 步补维度，无维度可补时按第 4 步问用户，不硬凑也不直接交付。
- `references/data-contract.md` 增“呈现计划”一节；`assets/02-报告模板.md` 末段与 `docs/index.md`（谁负责哪个环节、怎样验收）同步。

## 成本与取舍

- 呈现计划选**工作区工件**而非 report.json schema 字段（用户决策）：不推翻 115 的“业务 JSON 去图表化”，也不改 report.py；代价是机器不拦截，靠 review.md 人工核对（流程第 6 步已把呈现计划核对列为 review.md 必记内容）。被否决方案：presentation 数组进 schema 并由 report.py 校验引用与多样性。
- 图型配额**只写产教技能**（用户决策），交接时作为最低呈现要求传给渲染、交付前由本技能核对最终网页；report-rendering 保持 113 的“数据关系驱动、无配额”通用规则，不影响公众号、就业等其他报告技能。被否决方案：把 ≥2 图型/单型 ≤3 写进共享渲染技能。
- 编号流程比段落式更占篇幅、改写时需维护步骤间引用；换来的是可逐条核对、可判定跳步。
