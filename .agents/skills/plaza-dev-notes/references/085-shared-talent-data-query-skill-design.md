### 已发布的首期范围与设计差异

- 13 个实际指标以 capabilities 为准：岗位/企业数、学历/经验/招聘类型/来源/省/市分布、名称排名、学历×经验及城市×学历交叉、薪酬摘要/分布。最多四个具名样本，两组时计算兼容指标差值；比较组不同口径不会隐含合并。
- 薪酬先支持固定六档、最多六位原值小数、统一 100K/月上限与线性分位数；自定义分箱、分组薪酬与更多交叉不是已完成能力。专业映射、技能描述分析、职教预设、LQ 与 XLSX 仍属 P1。
- plan 解析与列出成本类别/查询数，不运行统计 COUNT，也未提供 EXPLAIN 结果接口。运行时注册表是指标权威，metrics.md 是维护的语义说明，首期未实现文档自动生成。
- 默认状态目录为 `web/server/workspace/.talent-query-state`，已 gitignore；部署可设 TALENT_QUERY_STATE_DIR。目录设置 setgid/组写，工件留本会话。重查询与元数据分别各限 1，作用于新入口；旧白名单未迁移队列，不能声称已限住全库所有客户端。
- 对相同读批次保存完整指标包，不拼混不同时点的缓存指标。cacheKey 含完整统计请求/引擎、数据源账户与字典解析指纹；不可变 snapshotId 绑定源、实际内容和读取时点，刷新查询缓存不会覆盖旧快照。snapshot-only 首期仍受最长 15min 新鲜度上限约束；长周期快照登记、刷新与状态目录保留/清理策略待扩展。
- 固定 SQL 由受信模板和 UTF-8 十六进制字面量生成，LIKE 显式转义通配符；未声称原生驱动参数绑定。多语句事务仅工具内部编译，不向 Agent 放开任意 SQL。复用当前客户端而不加驱动依赖；只读事务不代表现有账号权限已被收紧。
- 数据 hash 绑定规范化请求、样本、指标和质量；工件清单单独核对文件 SHA-256。它们是内容一致性检查，不是密码隔离或签名认证。内部证据不进公开导出，CSV 文本单元格防公式执行。

### 本轮确认的持久事实

产业字典存在 `pid=-1 / level=-1` 的顶层分类，不能作为坏 ID 直接拒绝；岗位和产业 ID 必须分命名空间。真实产业树中“机器人”同时出现在不同层级，whole-industry 可按唯一 level=0 候选选择 ID，不选同名细链；工具不会仅凭名称取第一个。地域统计在省份及已有城市别名归并后取 TOP N，否则相同代码可能被拆成多行。没有已核验城市编码的地域仍可查，code=null 不伪造边界。

**计时边界补注（2026-11-02）**：`db.mjs` 当前逐语句 elapsedMs 用 stdout begin/end 帧的客户端到达时差计算，受 mysql 输出缓冲影响，不能当作实际 SQL 执行耗时；已观察到真实全国统计批次耗时 176928ms，而该语句日志 elapsedMs=0。`execution.sqlBatchMs` 是整个客户端连接/统计批次耗时，仍包含建连、传输等开销。独立请求基准应从启动 CLI 前到进程关闭后，用单调时钟记录完整请求时间；不能将原逐语句值、工具落盘前的 totalMs 或两者之和伪装成完整请求/纯服务端 SQL 时长。后续需引入服务端时钟或可靠的执行端计时再验收逐语句性能字段。

**基准复现入口**：`reports/query-benchmarks/2026-11-02-five-industries/run.mjs` 为用户要求的五产业×四种地域/学历/经验条件共 20 条计数请求，严格串行、每项一次、live 绕过应用结果缓存；以完整请求单调时钟耗时为主，保存 SQL 批次耗时、状态/错误、实际 SQL 与原工件引用。`queries.json` 固化条件，`industry-mapping.json` 固化已解析的一级分类和字典版本；`--resume` 只接未完成项，`--rerun` 才显式重跑。首轮 **20/20** 真实查询全部成功，完成请求/原工件指纹/实际 SQL/CSV 交叉核验。raw/ 原工件在本机保留并 gitignore，可读清单/CSV/结果进入版本管理。它不是新 Skill API，不清数据库缓冲池、不声称冷库/p95；单次测量与运行细节留在该目录的结果，不另建运行观察手记。本补注不修改查询执行器/业务库。

**纯计数优化候选（2026-11-02，未接入）**：`compile.mjs:31` 起的 base SQL 即使只请求 positions.count 也带 MAX(update_time)、多个字段缺失量及地址 LEFT JOIN；全国计数可评估按需投影与省略无关关联。原基准 Q17 的只读 EXPLAIN 从在招索引开始（估计 698 万岗位），再关联地址及相关产业子查询；候选改写先按产业关系索引取 DISTINCT position_id，再主键关联岗位，仅求 COUNT，计划转为产业范围检索与候选回表。真实只读试跑数量与原 Q17 相同，详见同基准目录的 `optimization-probe.json`、`性能分析.md`；两次测量非同事务/受控缓存，不能将单例幅度作为通用承诺。后续优先验证该路径与最小投影，再合并同产业多样本条件聚合；当前同请求多个 cohort 仍逐组生成 base，连接复用不等于扫描复用。正式落地须同步处理被省略的元数据/校验语义，并回归全部 20 条。索引新增与预聚合仍属后续方案，本轮仅 SELECT/EXPLAIN 和分析文档，未改引擎/业务库。

## 动机与范围

就业指导、技术预测和公众号报告使用同一人才数据库，但重复维护连接、筛选、聚合、日期和证据逻辑；复用一套密码或把 SQL 文档搬进新目录，不能解决口径漂移和重复扫描。用户本轮要求先梳理现状，再设计独立数据库查询 Skill 的功能。

名称 **`talent-data-query`（人才数据库查询）**，定位为各业务 Skill 复用的数据能力，也支持直接回答库内统计问题。首期覆盖岗位、地域与产业；专业关联等数据域后续扩展，不以“通用数据库”名义承诺任意表、任意 SQL 或任意自然语言问题。

本记录细化并接替 [084](084-general-talent-analysis-skill-design.md) 中的共享查询部分；084 中分析组织与公众号呈现分离的方向保留。这里定义的是数据接口，不代替各业务 Skill 的报告协议。

### 本轮确认的共性问题

1. **隐含筛选已经影响跨行业查询**：`career-market-query.mjs:49–55` 默认广州、Java 及后端/服务端/开发；传入机器人关键词却未给 roleTerms 时仍添加软件岗位词，显式 `roleTerms:[]` 又在 `:57` 被拒绝。机器人、纺织快照的查询参数表确实记载这三个岗位词；因此这些快照应按实际窄口径理解，不能作为完整产业覆盖证明。迁移不能只换名称后继续复用其数字。
2. **分布截断改变比例**：`:163` 先按 `params.limit` 截断返回行，再在 `:105` 用剩余行求分母。离线 fixture 的三组计数 30/20/50，`limit=2` 返回 60%/40%，而非完整基数下的 30%/20%。这验证的是计算行为，不是真实学历数据。
3. **同名指标有不同算法**：`cohort-summary.sql:8` 的 salary_available 只要求两端正数；`salary-distribution.sql:20` 另剔除 max>100K；公众号 `fetch_data.py:289` 则先转整数、允许至 500K，并在 `:461` 用索引选取分位数；职业数据文档又规定加权线性插值。新的指标必须有版本，旧数字不能无声混拼。
4. **日期与输出类型不充分**：白名单 `:164` 把查询当天标为 snapshotDate；它不证明数据源在当天更新。批处理解析保留字符串计数，缺少稳定的单位、分母、缺失数和结果级指纹；SQL/参数又散落在日志、Markdown 与核查表中。
5. **重复扫描与大文本传输同时存在**：七类模板反复使用同样 WHERE/JOIN；公众号先拉全量 description，再为多维校验重查。旧 `mysql-query --max-rows` 只裁剪已返回结果，不限制数据库扫描；GROUP BY 后 LIMIT 也不意味着只处理少量岗位。
6. **工具成功和任务完整混淆**：白名单单项数据库失败在 `:165` 返回 `ok:false`，但 main 仍可能正常退出；批次结果没有统一的指标缺失与重试分类。调用方必须检查结果状态，不能只凭进程退出码或若干非空行宣告统计完成。

### 2026-11-02 的只读性能核验

- 读取六张相关表的索引元数据，41 行，工具记录 40ms。岗位表有 publish_state、update_time、企业等索引及岗位名 FULLTEXT；未发现以 company_address_id 为首列的索引。地址有 `(city,district)` 和以 province 开头的复合索引；产业关系有 `(industry_chain_id,position_id)`；专业关系有 professional_id、position_type_id 等索引。这些是当前结构，不是新增索引建议的充分依据。
- 广州 Java 后端学历聚合 EXPLAIN，工具记录 39ms：岗位表选择 publish_state_index，估计 rows=6,732,832，再主键关联地址并过滤城市；Extra 有 temporary/filesort。**估计候选行不是实际扫描行数，39ms 是 EXPLAIN 耗时，不是聚合耗时**。没有为性能测试执行全量聚合。
- 既有 017 的中文 FULLTEXT 召回限制仍需保留；不能用 MATCH 替换 LIKE 后只比较耗时而不比较集合。既有 016/技术快照记载的数十秒聚合是历史测量，不作今天的性能承诺。

## 二、职责与部署结构

调用关系：**业务 Skill → 共享查询 Skill 的请求规范 → 受信执行工具 → 数据库/受控结果缓存 → 标准结果 → 业务分析与图表**。

- **业务层**决定用户想比较什么、报告写给谁、采用什么分析与建议；就业指导的求职建议、技术预测的成熟度研判、公众号的文章与图片继续留在原 Skill。它提交样本条件和指标需求，消费 metricId，不自行查库或改写统计值。
- **共享 Skill**说明实体如何解析、各指标的语义、如何选择查询模式、如何处理歧义/空值/失败，以及输出如何引用。入口保持精简，详细字典、指标与协议按需读 references，不塞整份数据库手册或密码。
- **执行工具**确定性验证请求、解析有效字典与关联、编译查询、调度、计算、校验、缓存和落盘。数据库操作由代码执行；“调用另一个 Skill”不表示另起模型会话、子 Agent 或切换当前报告 Skill。
- **配置**沿用当前配置来源，先抽出共用配置解析，不再复制 `db_config.json` 给每个 Skill，也不让 Agent 阅读 `.env`。CLI 共用配置只是工程解耦；078 现有沙箱 ACL 仍允许读取 `.env`，不能宣称已经实现凭据隔离。后续专用 SELECT 账号与执行代理属于单独部署项。
- **部署**首期仍采用项目受信 CLI，复用 MySQL 客户端回落，不引入 HTTP/MCP 服务。先用受控模板与经过测试的参数字面量编码；现有 CLI 字符串拼接不能称为驱动原生参数绑定。更换为原生驱动/连接池需记录依赖取舍并实测；不把“加连接池”当主要提速手段。

最初建议的文件布局（下列路径已在首期建立）：

```text
.agents/skills/talent-data-query/
  SKILL.md
  references/request-contract.md       # 请求、结果、错误和新鲜度
  references/data-domains.md           # 已支持实体、关联、口径边界
  references/metrics.md                # 对应执行器能力清单，避免重复维护公式
scripts/talent-data-query.mjs          # Agent 与业务脚本共用的受信 CLI
scripts/talent-data/                   # 配置、解析、编译、执行、校验、缓存、适配
```

运行时代码的指标注册表及请求校验是权威；首期文档只解释语义，自动导出/一致性生成留作后续，不另实现一套统计公式。项目部署资源不需要每个业务 Skill 的独立 `.venv`；公众号渲染的 Python 环境仍可保留。

在线需修改 `web/server/index.ts:125` 起的工具声明，提供 CLI 与共享 Skill 文档的明确允许路径；核对 `web/server/lib/piRunner.ts:533` 当前只显式加载所选业务 Skill 的行为，保证共享文档可读，不能假定新增目录会自动加载。首期作为共享依赖，不自动加入 `SKILL_PROMPTS` 生成广场卡片，不新增表单；本地按普通 Skill 发现规则使用。

招聘类型 `SHIXI`、经验“在校/应届”与岗位名含“实习”的语义须分开；可提供具名 `student-entry/1` 组合规则，但不再让 internship=true 隐含混合三者。经验 LESS_THAN_3 保留“3 年以内”的原始上界含义；不自动写成互斥的“1–3 年”。学历“不限”、字段缺失和“可投”推断也分别处理。

岗位类型字典与产业链字典是两个命名空间；行业名称可解析产业链，用户说岗位类目则走岗位类型，不把人工智能 1242 与产业链人工智能 26 混用。专业关联得到的岗位类型仍可能存于主表逗号字符串，解析正确性和索引效率需单独实测；存在专业映射索引不证明终端岗位筛选可走索引。

地理查询能力与地图边界包分开：可查的省市不以广东/浙江资源包为限；未注册地图资源只影响绘图。返回标准编码、未识别地址桶和缺失量，不把缺失行补成 0；区域筛选使用企业关联地址，准确说明它与实际工作地的区别。

不承诺的能力：岗位真实新增/同比趋势、市场岗位总量、人才供需缺口、就业率、企业实际录用和无验证方法的专业匹配率。库内既有派生匹配百分比不能仅因存于数据库就作为实测指标发布。多期结构化快照可以比较“库内记录变化”，仍不能自动解释为市场需求增长。

### 首期核心指标的候选统一口径

- `cohort-policy/1`：默认在招且岗位未删除；按岗位主键统计记录，产业/专业关系用 EXISTS 或去重集合限制，不把关联条数当岗位数。企业数是该样本中非空有效企业 ID 的 distinct 数，另记缺失。无地域筛选时不能因为地址 JOIN 丢掉岗位；有地域筛选时仅匹配可归属的地址，并说明缺失地址无法归属目标地域。产业/专业覆盖率必须给出被检验的候选基数，不能在先筛出的映射命中集合中计算成 100%。
- `salary-policy/1`：候选默认沿用就业指导的 100K/月清洗上限，但补齐两端严格数值、`0 < min <= max <= 100` 的规则；空/非数值、非正数、倒置、超过阈值分别登记排除量，说明被排除不等于岗位不存在。其他上限只通过已注册、具名版本的策略选择，比较组必须同策略。读取时保留原字段有效小数精度，不先 CAST SIGNED；单位为人民币千元/月，中点为两端均值；中点平均数按岗位频数加权，分位数采用排序样本的线性插值 `h=(n-1)*p`，由未提前分箱/舍入的中点频数重建相邻秩。只有展示最后一步舍入；薪资有效率与所有薪酬指标使用同一有效性规则。实际源单位/精度仍需实现时用小样本核验。
- `category-policy/1`：保留原始枚举及稳定中文名、未知/缺失桶；展示合并值与原枚举对应关系可追溯。`share` 的内部范围为 0–1，展示为百分比时注明，跨组占比差以百分点输出；不沿用有时 ratio=百分数、有时 fraction=小数的隐含约定。

职教“可投宽口径”“明确大专/高职”和叠加经验门槛的“入门岗位池”是不同集合，分别命名与版本化，不能统一成一个含糊的 voc_pool 指标；共享层只统计给定集合，不把学历/经验满足推断为一定可录用。

这些是新版本候选口径，不追溯改写旧报告。旧白名单和公众号的历史算法保留 legacy 标识；切换后值不同需能用同一实际样本解释差异。

## 四、输入与操作协议（候选）

CLI 计划提供 `capabilities`、`resolve`、`plan`、`query`、`inspect`、`export` 六种操作。plan 仅校验、解析和估算，不运行全量 COUNT；必要时执行只读 EXPLAIN，明确估计性质。常见请求由 query 在内部完成解析与计划，避免模型为简单问题来回调用六次。请求使用文件输入，较大的 JSON 不拼进 shell 参数。

以下是 **`talent-query/1` 设计示例，不是已发布 API**：

```json
{
  "schema": "talent-query/1",
  "sourceId": "talent-main",
  "cohorts": [
    {
      "id": "gz",
      "filters": {
        "region": {"level": "city", "province": "广东省", "name": "广州市"},
        "title": {"any": ["机器人"], "all": [], "exclude": []},
        "state": "publishing"
      }
    },
    {
      "id": "fs",
      "filters": {
        "region": {"level": "city", "province": "广东省", "name": "佛山市"},
        "title": {"any": ["机器人"], "all": [], "exclude": []},
        "state": "publishing"
      }
    }
  ],
  "metrics": ["positions.count", "education.distribution", "salary.summary"],
  "policies": {"salary": "salary-policy/1", "consistency": "consistent-read"},
  "execution": {"freshness": "live", "deadlineMs": 240000},
  "output": {"previewRows": 20, "exports": []}
}
```

示例明确是**岗位名称包含机器人**的横截面，不是整个机器人产业；未出现的行业、软件岗位词、专业和时间窗不暗中加入。所有数值与 ID 由工具验证；名称存在会改变结果的歧义时返回候选，业务 Skill 再向用户澄清。零匹配是合法空集合，未识别实体则是解析未完成，两者状态不同。

`execution.freshness` 建议支持 `live`（业务统计重新读取数据库，仍可用已校验的字典缓存）、`cache-ok`（不超过 maxAge 的结果）、`snapshot-only`（指定已有快照，无数据库查询）。缓存过期或无匹配快照时明确返回不可用；不能悄悄换成近似地域或更旧的结果。预算有服务端硬上限，不能靠请求任意放大。

请求还需限制样本组数量、分组维度/基数、关键词/子树规模、指标数、文本样本量和输出字节；不接收自定义 SQL、表名、JOIN、自由表达式或工作区外的输出路径。CLI 候选退出码为 complete/empty=0、partial=3、needs_clarification/请求需修正=2、failed=1，并始终返回结构化状态；调用方仍须读取指标状态，不把任何非零码简单改写成“没有岗位”。

业务层可继续用 084 的 analysis-spec 描述分析目标、读者和交付类型，再转为本协议；查询接口不接收文章风格、图像主题、HTML 模板和微信账号。

## 五、输出形式：摘要、数据与证据分层

### 1. stdout 返回紧凑结果索引

返回 requestId、整体状态、规范化筛选摘要、各指标状态、必要的事实摘要/少量预览、实际文件清单、缓存/新鲜度与总耗时。默认不回显 SQL、全量岗位行或 description。完整 JSON 与证据在同一次执行落盘，Agent 根据任务读取需要的部分；`previewRows` 只裁剪展示，不改变统计基数或宣称计算全量。

建议工件为当前会话 `data/<requestId>/result.json`、`summary.md`、`manifest.json`，以及分开的内部 `evidence.json`、按需 `exports/`。路径由工具生成并限制在本会话允许目录，完整写入且指纹校验后才宣告成功；共享缓存为执行层维护，不能将另一会话的可变文件路径直接交给当前会话。JSON 是其他 Skill 的权威输入，Markdown 只是由其确定性生成的可读视图。

### 2. `talent-result/1` 的最小结构

| 字段 | 约定 |
|---|---|
| `schema / requestId / status` | 版本；本次执行标识；`complete / partial / empty / needs_clarification / failed`。partial 必须列出未完成指标；empty 只有在查询成功且样本为零时使用 |
| `request / resolvedEntities / cohorts` | 规范化请求、实际 ID/名称/关联路径、cohortId/指纹、计数单位、地区地址口径和缺失规则；未解析的实体不能进入执行 |
| `metrics[]` | `metricId / metricVersion / cohortId / status / kind / unit / value或rows / numerator / denominator / validN / missingN / excludedN / method / evidenceIds`；不适用字段省略，不用 0 填未知 |
| `comparisons[] / facts[]` | 可选的确定性差值、排名和事实摘要，引用输入 metricId；分母、单位或方法版本不兼容时拒绝计算 |
| `quality` | 校验清单、覆盖/缺失与异常、是否可用于声明的统计范围；缺失、空检查或截断计算结果不能 complete |
| `freshness` | `executedAt / dataReadAt / servedAt / sourceLatestUpdateAt / sourceTimestampMeaning / cacheAgeMs / mode`；源更新时间不详填 null；不能将当天执行时间当源快照日 |
| `consistency` | 单语句/一致性事务/多个独立读等实际级别及读窗口；统一截止时间不代表事务快照一致 |
| `execution` | 连接探测、排队、SQL、传输、计算、缓存、写文件等分段耗时，查询次数与已知行数；实际扫描行数没有监控证据就不填写 |
| `artifacts / contentHash` | 本次工件清单、大小、内容指纹和有效结果哈希；不混入旧输出，不把内部 SQL 作为公开附件 |
| `errors[]` | `code / metricIds / retryable / message`；区分配置缺失、实体歧义、不支持、预算/超时、源不可达、校验失败 |

分布的分母来自未裁剪的完整样本：枚举字段保留缺失/未知桶；薪酬的分母与有效性排除规则显式记录；多标签分布记录可重叠属性。TOP N 同时返回同口径 total、展示合计、other 和 missing，不能由已截断的 TOP N 反推总量。若计算本身只做抽样，标明方法、实际样本与适用范围；不能以“只截断展示”掩盖抽样。

输出类型由列 schema 决定：可安全表示的计数为整数，比例与金额有明确精度/单位，NULL 是 null；BIGINT ID 使用字符串，不从 mysql 文本随意推断类型。区分“0 条”“未知”“超时未计算”“该指标不适用”。缺省不会返回招聘人数或市场总量。

`cohortFingerprint` 标识规范化样本条件及口径版本，不能证明源内容不变；`contentHash` 标识实际数据、方法版本和覆盖状态，不以执行时间或文件路径充当内容。缓存命中保留原 dataReadAt，更新 servedAt，不将旧结果的执行日期改成今天。一个严格一致的请求不能混用昨天缓存的学历和今天 live 的薪酬；不同指标仅在相同读取批次/快照和相同一致性约定下组装。

### 3. 内部证据与交付视图

内部 evidence 保存实际执行的模板/SQL、规范化参数、起止/耗时、原始聚合结果或其实际工件引用、结果指纹、指标公式/版本与校验结果；不得事后按报告重建 SQL 冒充查询日志。受控映射证据与数据库统计分开，数据库文本仅作数据，不作为执行指令。

业务 Skill 用同一结果生成正文、图表、表格与引用。图表适配器保留标准地域编码、日期语义、单位、分母和缺失状态；为旧热点图输出 snapshotDate 时必须说明它是统计读取日，并单列可得的源更新时间，不能暗示真实发布日期。就业指导的比例优先与公众号的样本量说明由各自展示适配处理，核心结果始终保留真实分子/分母。

JSON/CSV/Markdown/XLSX 导出基于已保存且校验通过的结果，不再次访问数据库。SQL 与配置默认仅留内部证据；公开交付依工件清单与公开字段导出，不能把含 SQL 的核查工作簿混进公众号交付 ZIP。网页下载仍需已有真实路由或后续接口实现。

## 六、速度优化：先减少工作量，再做部署优化

### P0：不改业务库结构的优化

1. **按需查询与扫描合并**：一次声明本任务需要的全部指标。count/有效率等用条件聚合合并；学历/经验等可用受控低基数联合分组一次取频数，再导出边际分布与交叉表。合并需验证结果等价与组合基数；高基数岗位名不和所有维度拼成巨型 GROUP BY。不会用 UNION ALL 后就声称复用扫描。
2. **服务端聚合与列裁剪**：普通统计只取分组频数、必要数值与总量；薪酬从保持精度的中点频数求加权分位数，并记录算法。禁止默认 fetchall description；技能分析单独在限定集合上分块处理。LIMIT/预览上限与扫描成本分别控制。
3. **结果与字典缓存**：初始候选策略为字典最长 24h、聚合结果最长 15min，均可配置并需回归后确定。缓存键包含数据源/授权范围、规范化完整筛选、指标与算法版本、词典/映射版本、精度、时间基准和一致性要求；不同输出风格不影响相同统计结果复用。没有可靠源修订号时依 TTL 判新鲜，最大 update_time 不能证明源无删除或历史修改。live 跳过聚合结果缓存；旧快照不伪装实时。
4. **并发合并和全局调度**：相同请求同时到达时共享一次在途执行，完成后复制/引用不可变结果到各会话；不是每个 Skill 再查一次。每数据源重查询先限 1，轻查询最多 2，并设全局排队/截止预算；不能只在单个 CLI 内限 2 而允许多个会话无限叠加。需由服务端共享调度状态协调，单进程 CLI 退出即丢的 Map 不算跨会话缓存/全局限流。
5. **计划检查与单次连接批次**：复用现有客户端兼容探测，合适的指标在受控批次同连接执行；MySQL 5.7 不能依赖 8.x CTE、窗口/递归功能。支持时用同连接、合适隔离级别与只读一致性事务计算需要对账的多个指标；若底层引擎/适配器不支持则明示实际一致性，不能将多次新连接标成同一快照。只读路径不依赖临时表 CREATE 权限。
6. **预算与失败处理**：候选默认元数据 5s、单条聚合 120s/最长 180s、任务总预算 240s，具体还须与平台会话期限对齐。昂贵查询不先强制跑一遍同样昂贵的 COUNT；优先利用实际聚合/分布得到基数。只有可恢复连接故障且预算允许时有限重试；超时不自动重跑，也不静默改词或放宽地区来得到数字。

低基数联合分组、同连接事务、缓存和候选集合复用都要分别验证性能；同 WHERE/cohort 指纹只保证语义相同，不自动消除物理重复扫描。大候选集不能通过把全部岗位 ID 搬到应用、拼巨大 IN 列表来假装优化。

### P1/P2：需要独立验收的优化

- P1 建立结构化快照注册与刷新入口，tech-forecast 按自身 90 天等业务新鲜度要求选择可接受的快照。旧 Markdown 只有能还原完整实际筛选、指标方法和证据时才导入；不能按文件标题直接纳入通用结果缓存。
- P1 文本词命中使用经版本控制的行业词典/用户词表，记录大小写、词界、同义归并和命中单位；受限分块读取或可复现抽样。明确传输条数/字节、样本方法与缺失分母，不沿用“按 ID 每 40 行”便宣称随机误差。
- P2 若省域/全国任意中文模糊查询仍慢，再评估专用分析库、岗位类型关系规范化、中文检索索引、常用维度预聚合或索引调整。当前岗位地址索引形态和多对多去重提示这些方向值得测量，但本轮没有 DDL 授权/实施。
- 预聚合只服务能由其粒度准确回答的问题；任意关键词及交叉筛选仍回到明细或专门检索。增量刷新要处理在招状态变化、更新、删除与去重，不能只有新增；源最大时间戳不是完整变更日志。未建成的趋势数据不进入能力清单。

性能验证分别记录连接、SQL、传输、计算、缓存、排队与模型阅读开销。以相同集合和算法比较旧/新冷查询，再测热缓存及多会话并发；记录实际环境与样本，验收前不承诺全地域秒级。

## 七、迁移顺序与验收

1. **基础层**：抽出共享配置、受信执行适配、指标注册表和请求/结果校验；实现地域×岗位/产业、基础分布/薪酬、实际证据。旧 career-market-query 保留明确的 legacy 语义与输出，适配新执行层时逐项等价回归；新请求不继承旧默认词。旧 raw mysql 工具仍限开发排查，在线不新增任意 SQL 入口。
2. **就业指导试点**：用新结果填充岗位需求与热点图；保持原六章与用户展示规则，验证总量/分母/日期和失败呈现。数据库失败不能仅看 CLI 退出码，未完成指标必须出现在结果状态。
3. **技术预测迁移**：保留标准关键词与新兴/传统组的选择，明确 any/all，取消默认软件词；老快照按原实际条件保留版本，重新获取正确口径后另存，不篡改历史。公开来源、成熟度评分与预测保持在业务层。
4. **公众号迁移及扩展**：用结果适配器替代 fetch_data 的直连与统计，逐步扩充专业关联、技能文本与多标签交叉；核查表直接消费实际 evidence。083 中缺图、裁切、数据核验和打包缺陷仍须各自修复，抽取查询层不会自动解决它们。
5. **离线报告与部署**：industry-education-report 暂不改运行模式；需要新版实时版时再改版本/引用契约。验证低权 Pi 可调用受信入口、共享文档可读、工件只能落本会话，以及全局队列/缓存的多进程行为，再决定是否开放独立查询卡片。

验收用例至少包括：非广东同岗位比较；无行业限制；机器人/服装不被软件词收窄；未知地名与同名专业；同专业跨学制；产业多链/专业多岗位不重复计数；零结果/全缺薪酬/非法薪酬/未知枚举；截断 TOP N 的完整分母与其他；实习规则分离；跨指标一致性；缓存命中/过期/live 绕过与版本隔离；并发同请求只执行一次及重查询全局上限；超时/部分结果/重试终止；正文、图表、核查表和导出引用同一结果指纹。真实库核验先用小范围，性能大范围另设预算。

## 成本与取舍

- **采用共享 Skill + 确定性 CLI**：文档可指导模型理解业务语义，程序能统一数值与预算；代价是需要维护稳定接口、运行时可见路径和兼容适配。否决只创建一个“请查数据库”的 SKILL.md：它不能让多个调用者自动共享缓存、连接、口径或并发限制。
- **采用注册指标与受控组合**：首期会有不支持的问题，需扩展指标后回答；否决任意模型 SQL 和任意 schema 扫描作为在线通用性，避免把关联语义和查询成本留给模型猜测。
- **先保留现有客户端与部署形态**：减少接入成本，但 mysql 文本解析、参数编码、批次结果分隔和类型仍需真实回归；连接池或原生驱动可作为后续有证据的独立改造，不预设其能解决千万级低选择性扫描。
- **保留不可变证据与显式新鲜度**：增加存储、版本及清理成本，换取跨 Skill 复用和可追溯结果；缓存不等于实时，也不等于源数据质量已合格。公开字段与内部证据分层，增加导出适配但避免重复查询和内部 SQL 泄入交付物。
- **保留离线模式与业务展示差异**：旧模板和引用仍可复现；代价是新旧结果并存的迁移期。不以共享查询之名统一报告章节、强制所有业务查实时库或重做前端。

## 设计阶段验证与原后续路线

设计阶段完成：上述代码/文档静态核查；现有 CLI 的默认词/空 roleTerms/截断分母行为通过临时 mock mysql 客户端复现；真实库仅执行索引元数据 SELECT 与 EXPLAIN。该阶段未实现新 Skill；后续首期实现与验证见本记录开头。

原设计的扩展顺序继续有效：专业映射与文本功能 P1、数据库级性能改造 P2 各自验收后再把对应能力标为已实现，不以首期已有真实查询替代全部候选能力验收。
