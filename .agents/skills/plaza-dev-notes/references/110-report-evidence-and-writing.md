# 110 · 从读者要做的决定组织报告

**状态**　设计定稿，待实现。适用于承担分析或决策任务的报告技能。

## 动机

“为专业负责人判断是否增开实训课”与“为宣传部门介绍本地岗位需求”可以使用相同的招聘数据，却需要不同的证据和写法。现有产教报告允许在关键证据不足时交付带限制的草案。新约定把这个决定交还给用户。[产教报告的现有交付方式](109-industry-report-query-handoff.md)

## 取证和交付

1. 确认谁会读、读完要做什么决定，以及地区、时间和对象。任务中已经说清的直接采用。有两种理解且会改变取证方式时，先向用户澄清。
2. 按核心问题列所需证据及来源。岗位统计保留范围、分母和指标出处，文档保留能定位的原文及适用范围。按需使用数据库、知识库或用户附件。对材料逐项判断能回答什么、还缺什么，以及缺口会影响哪个判断。足以支持相反结论的材料同样可以回答问题。
3. 若在原范围内取证后，仍不足以回答核心问题，结束本轮，仅给出已知事实、关键缺口及其影响，请用户选择。**扩大范围或补充材料**时，说明拟增加的来源、地域或时期，按用户选定的范围补证，再次评估。**按现有证据继续生成**时，明确哪些问题可以作答，哪些保留为未决。用户回复前不生成终稿，继续生成的选择也不补足缺失的事实。已足以回答核心问题时，直接成稿，次要缺项在相关段落说明。
4. 现有在线对话可沿用单选卡及自由输入，普通文本入口列出同样的选择。提问所需内容沿用 `kind`、`question` 和 `options`。业务层须能区分等待用户、按新范围补证、按原范围继续三种情况，等待期间不调用成品构建。现有卡片类型见 `web/shared/chatQuestion.ts:6`，提示约定见 `web/server/lib/chatQuestion.ts:3`。[用户决策卡](095-chat-human-decisions.md)

## 总分总的写法

- **全文**开头先答读者最关心的问题，必要时带一句限定。中段按支撑这个判断的子问题组织，统计与文档各自说明了什么就写到什么程度。结尾综合各项发现，说明对读者决定的意义，给出行动、先后次序或改变建议的条件。摘要可在正文核实后撰写，成品仍放在最前面。
- **每个论证段**先写本段判断，再给可核对的数据、材料或两者，说明证据与判断的关系。段末收束到这项证据对读者意味着什么。简短段落可把解释和收束合在一句；图注、来源和方法说明按各自用途写。提升到更广的意义时，仍然受证据的地区、时间和对象约束。
- 组织好论证后，再决定哪些比较值得画图。数字和图文引用同一份已核结果，出稿前复核数字、出处和推断，排版后核对实际成品中的图例、图注和分页。公众号已有同源分析与全文总分总，见 `wechat-report/SKILL.md:30-39`（相对 `.agents/skills/`）。[公众号报告的论证与图文核对](099-multivariate-report-evidence-and-references.md)

## 成本与取舍

关键缺证时多一次对话，可以避免用户把证据不足的终稿拿去做决定。每个次要缺项都提问会拖慢交付，触发条件限定为会影响核心回答的缺口。段末要求交代意义，但不规定句数，避免同一句判断在段首、段末和篇末重复。

## 实施与验收

可先在产教报告的“定范围、备证据、复核交付”接入（`.agents/skills/industry-education-report/SKILL.md:8-17`），再适配公众号等报告的成品构建入口。待验证的场景包括证据充足直接成稿、关键缺证暂停且无新成品、用户扩大范围后重新评估、用户按原范围继续且保留未决项。成稿另需用真实报告审阅全文和段落的判断、证据与建议能否逐项对应。本次仅登记设计，未验证这些运行行为。
