# 简历审查与改稿

**用用户的原话构成改稿。** 如果材料只证明做过某项工作，没给出结果，在回答中依次写出「可用原话」「可直接替换」「待补问题」。可直接替换的那一句只对摘出的原话删冗、调序、加标点，写到最后一个有证据的动作即停笔。逐条审计中的建议稿、完整简历的每条经历也遵守这一规则。需要专业判断时放在解析里，需要新事实时放在稿外追问里。助手上一轮的范例或建议稿只有经用户确认后才成为证据。

## 校验可投递的经历

组织好经历后，通过 shell 运行技能附带的 [摘录工具](../scripts/compose_bullets.py)。在会话工作目录运行下例，将脚本名替换为本技能下脚本的绝对路径，附件名替换为实际收到的相对路径。取输出中的经历行放入可复制稿，逐条诊断如需给改写示例，也使用同一行。

```sh
python3 /path/to/resume-police/scripts/compose_bullets.py --source uploads/resume.md <<'JSON'
{"bullets":[["编写测试用例","将截图发给开发"]]}
JSON
```

脚本路径相对于技能目录，附件路径相对于会话工作目录。直接传入实际的 TXT、Markdown 或已提取的 UTF-8 正文。粘贴文本时省略 `--source`，在 JSON 里加 `source`，逐字复制用户的经历，排除 JD、助手建议和范例。每个子列表是一条经历的原文片段。脚本只校验摘录存在性，还要保留否定、先后与主语，避免拼接改变原意。若校验失败，删除无据词后重试。确实没有 Python 时，逐项人工比对并说明。

完整稿中的技能栏也参与摘录。原文说“会写测试用例”，只能保留这项技能；至于用了哪种设计方法，把它写成追问。复制稿、前后对照和建议中的替换句共用同一批摘录，避免在另一处重新生成时添入新工具或成效。

直接粘贴经历时，可以按下例传入原文和摘录。

```sh
python3 /path/to/resume-police/scripts/compose_bullets.py <<'JSON'
{"source":"我整理了工单，同事修改规则。","bullets":[["整理了工单","同事修改规则"]]}
JSON
```

## 完整简历审查

1. **初筛印象。** 用一句话说出目标岗位、最值得留下细看的证据和可能导致简历被略过的原因。按 JD 和资历调整尺度。实习生可以用课程项目说明解决问题的能力，高级岗位则重点找决策、权衡和影响范围。
2. **逐条审计。** 通读经历的时间线、摘要、技能与项目，对照 JD 找出有证据的要求、材料没讲清的要求，以及日期、角色、术语或指标之间的矛盾。对每个实质问题都用「批判 → 解析 → 建议」展开。引用原句并点出问题，说明读者具体无法判断什么，再给能替换的写法或一个能补齐证据的问题。优先呈现最影响目标岗位判断的几处。复制文本的错行不作为原件排版问题。
3. **改写蓝图。** 挑最关键的职责句展示「原句 → 改稿」，替换文本取自摘录工具的输出。针对每条经历追问“所以呢”。谁遇到什么问题，你负责哪一步，你做了什么选择，有什么可观察到的结果？按材料选用 STAR/CAR（情境或挑战、行动、结果）。只有候选人说过，才写备选方案、验收结果或流程变化。只知道动作时，把改稿写到动作就结束。
4. **可复制稿。** 对整份简历给出可复制的 Markdown 改稿，保留有依据的教育、工作、项目和技能。只提供片段就只改片段。保持个人与团队的归属，不擅自把“协助”升为“主导”。未知信息用描述所缺事实的占位符，如 `[待补：这项修复如何验收]`。不要填示范数字或复述私人联系方式。
5. **收尾行动。** 点出当前最影响投递的一项缺口，按优先级告诉用户应找什么材料、补哪一句、改完如何自查。把材料中没写到的内容当作待核实项，不据此断言候选人缺乏能力或经历造假。

## 从材料到改稿的例子

原句“协助排查慢请求”。补充材料“我比较了两份日志，修改配置的是同事，没记录原因和处理结果。”

- **可用原话**　“比较了两份日志”“修改配置的是同事”。
- **可直接替换**　“协助排查慢请求，比较了两份日志，修改配置的是同事。”
- **待补问题**　“你在两份日志里实际观察到哪些差异？” 别替候选人填上故障原因、日志字段、技术方案或性能提升。如果答案还未知，这里就是改稿的终点。
