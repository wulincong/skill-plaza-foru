# 根据简历出面试题

先从用户提交的原始材料或之后确认的事实中引用项目陈述，说明它与哪条岗位要求相关、读者还缺什么证据。不能拿助手此前的建议稿代替原文。没有 JD 就限定为“根据简历出题”。材料有疑点时用问题验证，保留几种可能解释。例如团队上线了一个服务，仍需问清候选人交付了哪一部分。

## 精简笔录（V2）

适合“帮我准备面试官会问的问题”。先给一句判断和最多三项待核实的问题，再按重要性列出考察领域、对应经历或 JD 要求及优先级。由具体实现问到取舍。每道主问题配两三个有条件的追问与评价要点，说明什么样的回答能澄清贡献。让追问接住一种**可能**的回答，不把尚未说过的话归给候选人。

完整题单可用上游的 15–20 道规模，其中约八成紧扣岗位或关键项目。只有简历确实列了相关技能时，才选 2–4 道非核心技能题考察广度。用户指定题数或材料只够支撑少数好问题时按实际范围缩短。

## 项目深挖（V1）

适合“围绕项目做深挖”“给面试官评分依据”。把简历与 JD 交叉核对，列出需要验证的说法和验证方式，选最多两个核心项目，用 P.O.S.E.R. 串起追问。

| 维度 | 要问清什么 |
| --- | --- |
| Problem | 谁遇到了什么问题，团队如何判断做成了？ |
| Ownership | 哪一步由本人交付，与同事的分工和接口在哪里？ |
| Scale & Complexity | 规模怎么测，峰值和平均值怎样区分，真正的难点在哪里？ |
| Engineering Choices | 当时有哪些备选方案，受什么约束，为何接受这一取舍？ |
| Results & Retrospective | 怎样验证改动有效，有什么失败或遗留问题，重做会改哪里？ |

完整深挖可做八道主问题，五道追溯项目与技术细节，三道沿实际约束变化延伸并注明“假设”。每题带出处、考察目的、衍生追问和可观察的评分依据。用优秀、充分、待补等回答示例解释分档，不给尚未作答的人打分。

例如简历只写“优化了慢查询”。可以问“挑一条你参与处理的查询，你怎样定位耗时，具体改了哪部分？”若对方说调整了索引，再追问“你比较了哪些执行计划？怎样确认收益来自这次改动？”评分看能否说清本人的操作、比较条件与验证方式。项目中是否使用索引，要等回答确认。
